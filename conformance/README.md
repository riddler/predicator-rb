# The vendored conformance corpus

This directory holds the conformance material this package is checked
against. Most of it is copied, byte for byte, from two other repositories at
named tags; four files are this repository's own. A copied file is never
edited here: not a case, not a schema, not a reformat and not a
trailing-newline fix.

## What is copied, and from where

From [riddler/predicator-ex](https://github.com/riddler/predicator-ex), the
reference implementation, at the tag `SOURCE.json` names:

- `manifest.json` - the corpus hash, the instruction-set version, and one
  entry per tier naming its file, the opcodes it unlocks and its case count.
- `corpus/tier-1.json` to `corpus/tier-9.json` - the cases, one JSON object
  per line (newline-delimited JSON, not a JSON array).
- `schema/case.json`, `schema/corpus.json`, `schema/manifest.json`,
  `schema/registry.json` and `schema/report.json` - the reference's schemas
  for an authored case, a case as the tier files carry it, the manifest, a
  registry and a runner's report.

The tag carries other conformance material beside these: the authored case
sources the tier files are generated from, a worked-example registry, and the
files of a third surface (the analysis surface) that sit outside the corpus
hash. This package reads none of them, so none is copied.

From [riddler/predicator-ts](https://github.com/riddler/predicator-ts), the
TypeScript sibling, at the tag `transcript/VENDORED.json` names:

- `transcript/compile.json` and `transcript/compile-SOURCE.json` - what the
  reference compiles, refuses and renders over an authored list of sources no
  corpus case reaches, and the record of the run that wrote it.
- `transcript/tokens.json` and `transcript/tokens-SOURCE.json` - what the
  reference's lexer answers for a list of sources, and its record.

Each transcript was generated by running the reference itself; the copied
records name the reference's tag and commit they were run at, which is not
the tag `SOURCE.json` names when the two corpus releases share one corpus
hash (the check below requires that hash to be the vendored one). The
records are copied as they are and never re-stamped.

## What is this repository's own

- `SOURCE.json` - which copy of the corpus this is: the repository, the tag,
  the commit that tag resolves to, and the corpus hash and instruction-set
  version read out of the copied manifest. A tag identifies bytes and a
  branch does not, which is why a tag is what is recorded.
- `transcript/VENDORED.json` - which copy of the transcripts this is: the
  repository, the tag, the commit that tag resolves to, the directory they
  were copied from, and each copied file's SHA-256.
- `registry.json` - the record of which cases this package passes, on which
  surface, against which corpus. It is written only by `rake ratchet`, from a
  run it makes, and never by hand.
- `README.md` - this file.

The code that reads all of it lives under `test/conformance/`: the corpus
loader, the runner, the checks and the ratchet. None of it, and nothing in
this directory, is part of the gem.

## The checks

`rake corpus:check`, a stage of the full gate, holds the copies to their
records:

- The SHA-256 of the tier files' bytes, concatenated in ascending tier
  order, equals the corpus hash in `manifest.json` and the one in
  `SOURCE.json`; each tier file holds its tier's `case_count` lines; no tier
  file sits in `corpus/` that the manifest does not list.
- Each transcript file's SHA-256 equals the one `transcript/VENDORED.json`
  records, every file in `transcript/` is listed there, and each
  transcript's own record carries the same hash in its `transcript_hash`,
  the vendored corpus's hash in its `corpus_hash`, and the transcript's line
  count in `counts.rows`.

A mismatch fails the gate naming the field that disagrees. It is never
repaired by rewriting a hash: the hash is what a claim of conformance is
anchored to, and a hash rewritten to match whatever is on disk anchors it to
nothing. The fix is to restore the copied bytes, or to vendor a new tag.

The test suite runs every case of every tier on the evaluator surface, and
every case whose `source` is not null on the compiler surface, with no skip
list; a case carrying a key `schema/corpus.json` does not allow is refused
rather than half-read. Each case is answered pass or fail, and the run
prints, per surface, how many cases have no registry entry yet.

`rake registry`, also a stage of the full gate, holds `registry.json` to the
checks the reference's `RATCHET.md` gives a registry: its pin is the
manifest's corpus hash, its entries and claims are sorted and encoded one per
line as that document requires, every entry names a case of its surface at
the case's tier, every entry still passes in a run made now, and a claim of
tier N has an entry for every case it covers. `rake ratchet` is the one
writer: it runs both surfaces and adds every observed pass, refuses to drop
an entry that no longer passes, and writes a claim (`rake
"ratchet[evaluator:1]"`) only when the entries support it.

## The contract

The reference's `conformance/README.md` is the corpus contract (the two
surfaces, the tagged-value encoding, the cumulative tiers, retired cases and
the never-skip rule) and its `conformance/RATCHET.md` is the registry
contract. Read both at the tag `SOURCE.json` records, not at the reference's
default branch, because the copy here is that tag's. Where this file and
those documents disagree, they win.

## Refreshing to a new tag

A refresh is a deliberate, reviewed change, made by a person:

1. Copy each file listed above out of the new tag itself, byte for byte
   (`git show <tag>:conformance/<path> > <path>` in a clone of the source
   repository), never through an editor.
2. Re-record: write the new tag, its commit and the manifest's corpus hash
   and instruction-set version into `SOURCE.json`, or the new tag, commit and
   file hashes into `transcript/VENDORED.json`.
3. Run `rake corpus:check`, then the full gate, and read the diff like any
   other. A corpus whose hash moved also moves the registry's pin, so `rake
   ratchet` is run in the same change; it re-pins the registry and refuses if
   an entry no longer passes.

Nothing in the build, the suite or the gate fetches from either repository
or updates these files as a side effect of anything else.
